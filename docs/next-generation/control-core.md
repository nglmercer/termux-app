# Control core: current implementation

The in-process core is created by `TermuxService`. It supports protocol version 1, capability enumeration, `session.list`, `session.create`, `session.rename`, `session.resize`, `session.close`, and bounded binary `session.write`. It advertises close only while the local opt-in is enabled. Snapshots contain session handle, custom name, state and shell PID; they do not include command arguments, environment, terminal output or files. A handle identifies a live service session, not a process that can be resurrected.

The backend must run on the main thread. It takes a short service lock to inspect session membership and releases it before enqueueing input. Writes use the specified session handle and the existing terminal input queue; a rejected frame returns a backpressure error. Resize is limited to initialized running sessions and returns a conflict when the local activity visibly displays the target; local UI geometry takes precedence and is restored when the activity returns. Multi-client resize arbitration is not implemented. There is no event stream, attachment, command, file, process, Binder, or network transport in this implementation.

Scopes passed to this in-process API are assertions by a trusted caller, not authentication. A future transport must authenticate peers and derive scopes from its own authorization state; it must never accept a client-supplied set of scopes as proof. The same-UID local socket exposes a scoped subset only after user opt-in; no third-party exported component is added. Legacy RUN_COMMAND permissions and behavior are unchanged. Device tests for service destruction, session exit, concurrent callers and queue saturation remain required before exposing it externally.

Focused test command on the Termux development host:

```sh
. ~/android-sdk/env.sh
./gradlew :app:testDebugUnitTest --tests com.termux.app.control.ControlCoreTest -Pandroid.aapt2FromMavenOverride=/data/data/com.termux/files/usr/bin/aapt2
```

The focused test command ran successfully on the Termux host. It uses a fake backend for authorization and frame tests and does not verify Android service or PTY lifecycle behavior.

`session.close` sends SIGKILL to the session shell through a Linux pidfd and returns when the signal is accepted, not when the process is reaped. Process handles are disabled by default. The local-control dialog offers a separate unchecked force-close option for read/write access; it applies only to sessions created and started during the same opt-in interval. Existing sessions, unsupported kernels and denied syscalls return an unavailable error. Disabling the setting revokes control close and closes existing process handles. The transport must never enable this setting on a client's behalf. Other existing UI shutdown paths still use numeric PIDs and retain the exit/reuse race. JNI and multi-ABI packaging, permission behavior, process exit races and Android devices need testing before external exposure.

A local syscall smoke test can be compiled with `clang -std=c11 -D_GNU_SOURCE -Wall -Wextra -Werror terminal-emulator/src/test/native/pidfd-smoke.c -o build/pidfd-smoke` and run as `build/pidfd-smoke`. It forks a disposable child, signals it through a pidfd, and checks that a signal after exit fails. This exercises kernel syscalls only, not the JNI bridge, service lifecycle or APK packaging. The test passed on the current Termux host; the feature remains disabled by default.

`session.create` starts the existing default shell with the configured default working directory and bounded geometry. It enforces the same eight-session limit as the activity. An initialization failure before a PID exists removes the new non-plugin entry; a failure after startup leaves the session registered for its existing lifecycle. No command, environment, or arbitrary working directory is accepted. Live service, native failure rollback, activity attachment and multi-client tests remain required.

The optional IPC work has a standalone four-byte big-endian length-prefixed `FrameCodec` with a configurable maximum capped at 1 MiB. It rejects zero-length, oversized and truncated frames before dispatch. A strict single-request JSON-RPC parser rejects invalid UTF-8, duplicate keys, malformed JSON, excessive depth and oversized requests; a per-connection state requires version 1 negotiation first. The single-request JSON dispatcher serializes responses and derives scopes from its trusted caller; terminal bytes are never included in JSON. JSON-RPC batch requests are not implemented. An opt-in filesystem socket implementation checks same-UID peer credentials, bounds clients and frames, applies per-frame and dispatch deadlines and per-client request-rate limits, and closes clients on stop. The terminal context menu offers read-only or read/write access for the current service lifetime; it is disabled by default, and all processes with the app UID share the selected access. The native client is a prototype and is not packaged. Push output streaming, real-device permission/lifecycle tests and additional security review remain required before release.

`ServiceThreadDispatch` bounds queued service-thread calls at 20 and rejects waits from the service thread. A deadline before execution cancels the queued action; a deadline after execution starts returns an unknown outcome, which must not be retried automatically. It is wired to the service main handler but does not itself start a listener. The tests use an executor, not a real Android socket or PTY.

The local socket is at `files/control-ipc/control.sock` under the app private directory. It is disabled by default, receives scopes only from a trusted in-process caller, and never replaces a pre-existing path; a stale path after process death must be investigated and removed before restart. Connection revocation stops the listener and closes clients. Requests already executing at shutdown can have an unknown outcome. The protocol loop has JVM tests for UID rejection, negotiation, scoped operations, malformed requests and stopping before dispatch. The actual Android socket, OS-provided credentials and filesystem permissions have not been exercised on a device.

A native `tools/termux-control` client prototype negotiates the protocol, verifies the socket peer UID, bounds frames and deadlines, and exposes the current metadata operations. Its mock-socket tests run on the host; it is not packaged into `$PREFIX/bin` and supports bounded binary input and polling output, but not full terminal attachment. See its README for build and packaging limits.

A `session.write` request has named `id` and `length` parameters. After the metadata frame, the client sends one separate big-endian length-prefixed binary frame of exactly that length (1–65536 bytes), then receives the JSON-RPC response. Negotiation, scope and metadata are checked before reading the binary frame; a denied or malformed request closes the connection. No byte is added or interpreted as an Enter key by the client or server. The protocol loop is tested with simulated streams, and a host Unix socket test exercises the native client against the Java loop. Neither validates Android LocalSocket credentials or a live PTY.

## Opt-in output replay foundation

A session can allocate a 256 KiB in-memory raw PTY output ring through a trusted in-process call. It is disabled by default, stores only output observed after opt-in, overwrites oldest bytes when full, and reports an offset gap to readers. Reads return at most 64 KiB and never wait for additional output. Disabling replay or ending the session revokes readers and clears the ring. Output can include secrets; a transport must enforce a separate, explicit transcript scope before exposing it.

An in-process subscription manager requires a distinct `SESSIONS_OUTPUT` scope, shares one ring per session across authorized clients, limits clients and subscriptions, and closes each ring after its last ordinary subscriber disconnects, its optional resume window expires, or the service is destroyed. Transports must derive scopes from authenticated policy and close clients on disconnect. The local-control dialog offers a separate, unchecked output-access option; when selected, same-UID clients receive that scope. Authenticated socket clients can subscribe, read bounded chunks and unsubscribe. Closing a connection posts subscription cleanup to the service thread; the service also revokes all subscriptions on shutdown. The native CLI `follow` command consumes it and writes raw bytes to stdout. It is not a terminal screen snapshot and cannot reconstruct pre-attachment history or provide lossless replay after a gap. Unit tests cover ring behavior, not Android PTY concurrency or an actual socket.


The output methods are `session.output.subscribe` and `session.output.unsubscribe` with `{"id":"session-handle"}`, and `session.output.read` with `{"id":"session-handle","offset":0,"limit":65536}`. A successful read returns JSON metadata (`offset`, `nextOffset`, `endOffset`, `gap`, `length`) followed by one binary frame only when `length` is nonzero. Clients must read the next offset and handle `gap`; offsets refer only to bytes captured since replay was enabled and are not a screen snapshot. A connection may subscribe to at most four sessions and output is never sent under the ordinary session-read scope. Active connections no longer have a fixed lifetime or request-count cutoff. Each incoming frame has a five-second absolute deadline, and each connection is limited to 50 requests per second after a burst of 100. Ordinary subscriptions do not survive reconnects; the separately authorized resume option below provides bounded, best-effort continuity.

Socket tests use simulated streams and peer UIDs; Android peer credentials, UI consent, permission revocation, disconnect races and live PTY output remain unverified on a device. This polling prototype does not implement push events or a full terminal screen snapshot; optional bounded replay is described below.

The native `termux-control follow ID` command subscribes and polls output, writes binary bytes to stdout and reports overwritten gaps to stderr. By default it does not reconnect or restore a screen, and it should not write into the same session being followed because that can feed its own output back into the PTY. Host tests cover malformed metadata and framing and use a simulated Java socket; device and live PTY tests remain required.

The local-control dialog grants `SESSIONS_CLOSE` only when read/write access and the separate force-close checkbox are both selected. Both `SESSIONS_WRITE` and `SESSIONS_CLOSE` are required for `session.close`, and capability discovery omits it for clients lacking either scope. The signal is SIGKILL to the shell only; a successful reply means the signal was accepted, not that every descendant exited or that the session has been reaped. The listener stop, failed startup and service shutdown revoke the option and release handles. Sessions created before opt-in, or started after that opt-in was revoked and restarted, cannot acquire a handle. Existing sessions and kernels or security policies without working pidfd support return unavailable; there is no numeric-PID fallback. Android socket consent, pidfd behavior, revocation races, service lifecycle and UI still require device tests.

The native CLI also has a draft `attach ID` mode for an independent local terminal. It checks the target session PID and visible terminal/ancestor identity before subscribing, uses raw local input with a Ctrl-] then `.` detach escape, forwards bounded binary frames, and attempts to synchronize geometry. The client restores terminal mode on normal exit, handled signals and suspension. Identity checks cannot detect every indirect forwarding loop, such as a multiplexer displayed inside the target; use a genuinely independent terminal. Attachment uses polling, has no screen snapshot, reports output gaps, and normally stops on disconnect. Optional resume is described below. Host pseudo-terminal and mock/Java protocol tests do not replace Android or live-PTY validation.

The per-frame input deadline includes time spent receiving a partial header or body, so sending occasional bytes does not extend it. Rate-limit waits happen on socket workers, not the service thread; stopping the listener interrupts workers and closes clients. These are host-tested policies; actual Android LocalSocket timeouts, shutdown behavior, slow readers, prolonged attachments and battery impact require device testing. Socket output uses the platform send timeout and is not a verified absolute write deadline.

## Optional short output-resume window

The local-control dialog has a separate, unchecked option to allow a 15-second output-resume window after a client disconnects. It is available only with output access. A client must explicitly request `session.output.subscribe` with `{"id":"session-handle","resumable":true}`; the response returns a random `resumeToken`. On a new authenticated, output-resume-scoped connection, `session.output.resume` with `{"id":"session-handle","token":"..."}` reattaches to the same bounded output ring. Continue reading from the previously acknowledged offset and handle a possible gap. Tokens are bearer secrets: do not log or share them. They are generated on a socket worker and are neither persisted nor sent in logs.

A disconnected ticket permits resumption for 15 seconds of elapsed time; explicit unsubscribe removes the ticket immediately. Android may suspend the process and delay the scheduled memory cleanup, but overdue tickets are rejected when it resumes. Retained subscriptions count against the existing 32-subscription quota. Only one client may own a ticket at a time; a resume racing disconnect cleanup returns a conflict. Listener stop and failed startup revoke tickets and clear detached rings; active subscriptions are cleared when their client cleanup runs. Service destruction closes the registry. A session exit, full buffer, expiry, revoked scope or process death can prevent replay or cause gaps. Existing ordinary subscriptions still release their output immediately on disconnect. This same-UID prototype is not a cross-principal authorization scheme for future remote transports. The native client can request resume with its explicit `--resume` option and retries read-side transport failures; it never retries an uncertain input write. A failed resize or write ends attachment. Reconnection does not restore terminal screen history. Android timing, revocation, credential checks and live PTY behavior remain unverified on a device.
