# Extra-key editor model (in progress)

`ExtraKeyLayout` is an in-memory model for the existing `extra-keys` array. It accepts representative upstream JSON-like single-quoted and unquoted syntax, checks one to three rows with up to 24 keys per row, and preserves complete key objects—including unknown fields, macros, display names and nested popup objects—when moving them. It rejects duplicate object fields, malformed keys and oversized or overly complex input. It exports valid JSON accepted in principle by the existing extra-key format; exact Android parser compatibility still requires device or Android framework tests. Layouts outside these limits are rejected for editing and must not be silently replaced.

The model provides Classic, Coding, Vim, Tmux and Compact starting layouts, plus row/key add, remove and move operations. A user-edited configuration can serve as a custom layout. An unconnected persistence layer can read a caller-selected properties file, validate an append-only override, create a private backup, and check file identity and contents before appending. It does not yet choose the active Termux properties path or expose a save UI. Preview, hot reload, a visual editor, named profiles, and file import/export are also missing. Those are required before this workstream is complete.

`./gradlew :app:testDebugUnitTest --tests com.termux.app.extrakeys.ExtraKeyLayoutTest` tests representative parsing, presets, field preservation, defensive copying and bounds. It does not exercise the Android view or actual properties files.

The save path opens the final file with `O_NOFOLLOW`, rejects non-regular, differently owned or hard-linked files, never truncates the original, and reports a changed snapshot as a conflict. It writes a private backup before appending. Invalid UTF-8, malformed properties, oversized input and a final unfinished continuation are rejected. A partial write, sync failure or changed path after writing is reported as an uncertain outcome with the backup path so a caller can inspect before retrying. Failed backups may leave an incomplete backup file.

The checks cannot atomically exclude a shell process that modifies the file between the final comparison and append; external writers do not necessarily honor advisory locks. A caller must recheck primary/secondary properties-file precedence, explain this limitation, and perform all file I/O off the UI thread. Ancestor directory symlinks and Android platform behavior require further review. The Android instrumentation tests cover backups, conflicts, new-file permissions and final-component links but have not been run on a device.
